# AGENTS.md

Инструкции для coding-агентов, работающих в репозитории VoxNote.

## 1. Область действия

Этот файл действует для всего репозитория. Перед изменениями обязательно прочитайте:

1. `PROJECT_SPEC.md` — источник продуктовых требований;
2. `IMPLEMENTATION_PLAN.md` — порядок реализации и критерии этапов;
3. более локальный `AGENTS.md`, если он появится в изменяемом подкаталоге.

Если документы противоречат друг другу, не выбирайте трактовку молча. Сохраните безопасное текущее поведение, укажите противоречие и запросите решение.

## 2. Цель проекта

VoxNote — open-source приложение Windows для полностью локальной транскрибации русскоязычных аудиозаписей. Аудио, словари и текст пользователя не должны отправляться во внешние сервисы.

## 3. Зафиксированный стек

- Python 3.11 (headless sidecar ML-ядро);
- Tauri 2 (десктопная оболочка на Rust);
- React, TypeScript, Tailwind CSS, Lucide icons (пользовательский интерфейс, решение владельца проекта от 18.11.2026);
- faster-whisper, CTranslate2, PyAV;
- локальный типизированный IPC (JSON-RPC);
- pytest, Ruff, mypy;
- Windows 10/11 x64.

## 4. Основные продуктовые ограничения

- поддерживаются только `.m4a`, `.mp3`, `.wav`, `.flac`, `.ogg`;
- распознаётся русская речь;
- результат — единый текст без таймкодов и спикеров;
- модели MVP: `small`, `turbo`, `large-v3`;
- модель не входит в установщик;
- NVIDIA GPU используется при совместимости, иначе доступен CPU;
- пользователь может выбрать медицинский или собственный словарь;
- словарь является подсказкой, а не механизмом безусловной замены;
- телеметрия отсутствует;
- сетевые запросы во время транскрибации запрещены;
- UI поддерживает светлую, тёмную и системную темы;
- UI поддерживает снижение анимаций.

## 5. Язык и стиль

- пользовательский интерфейс и пользовательские ошибки пишутся по-русски;
- код, имена модулей, классов и функций пишутся по-английски;
- комментарии объясняют причину решения, а не повторяют код;
- документация проекта ведётся по-русски, если конкретный файл не предназначен для международной аудитории;
- сохраняйте файлы в UTF-8;
- не используйте транслит в именах API.

## 6. Рабочий процесс агента

Перед правкой:

1. проверьте состояние рабочего дерева;
2. прочитайте затрагиваемые файлы целиком;
3. определите активный этап из `IMPLEMENTATION_PLAN.md`;
4. найдите существующие тесты и архитектурные границы;
5. убедитесь, что не перезаписываете пользовательские изменения.

Во время работы:

1. реализуйте минимальный законченный срез;
2. не расширяйте задачу несвязанным рефакторингом;
3. держите UI, доменную логику и интеграции разделёнными;
4. добавляйте тесты одновременно с поведением;
5. сохраняйте приложение запускаемым после каждого логического шага.

После работы:

1. запустите наиболее узкие релевантные тесты;
2. запустите общий набор доступных проверок;
3. проверьте отсутствие случайных больших файлов и секретов;
4. обновите документацию, если поведение изменилось;
5. сообщите, что проверено, что не проверено и почему.

## 7. Архитектурные правила

- Фронтенд (React UI) не вызывает faster-whisper напрямую, а взаимодействует с Python-sidecar через типизированный IPC.
- Интеграция с faster-whisper находится за адаптером.
- UI получает неизменяемые снимки состояния и события контроллера.
- Состояния приложения переключает `AppStateMachine`, а не отдельные React-компоненты.
- Долгие операции не выполняются в UI-потоке.
- Пути пользовательских данных определяются одним сервисом.
- Работа с сетью изолирована в менеджере моделей и обновлений.
- Экспорт текста не зависит от конкретного UI.
- Технические ошибки преобразуются в типизированные ошибки домена до передачи интерфейсу.

Предпочтительные границы:

```text
React UI (Tauri 2)
  -> Typed IPC Client (JSON-RPC)
    -> Python Sidecar (Application Controller / State Machine)
      -> Domain Services
        -> Infrastructure Adapters (faster-whisper, PyAV, CUDA)
```

## 8. Прогресс и ETA

- не создавайте искусственный процент по таймеру;
- прогресс транскрибации основан на обработанной временной позиции аудио;
- прогресс загрузки основан на реально полученных байтах;
- если общий объём неизвестен, используйте неопределённое состояние;
- отображаемый процент не уменьшается;
- `100%` разрешён только после успешной финализации текста;
- ETA появляется только после накопления достаточных данных;
- ETA сглаживается и сбрасывается после существенного изменения скорости;
- при отсутствии событий backend декоративное движение останавливается;
- обновления UI ограничиваются разумной частотой.

Эти правила являются функциональными требованиями, а не косметическими рекомендациями.

## 9. Анимации и стилизация UI

- используйте дизайн-токены и motion-токены из `PROJECT_SPEC.md` и Tailwind-конфигурации;
- анимируйте простые свойства: opacity, transform, scale и color через CSS-transitions / Framer Motion;
- не используйте бесконечное движение для остановившегося процесса;
- каждое состояние должно быть понятно без анимации;
- reduced motion (`prefers-reduced-motion`) отключает циклические эффекты;
- числовой прогресс использует табличные цифры (`tabular-nums` / `font-features: "tnum"`);
- не меняйте размеры элементов при обновлении процентов и ETA.

## 10. Фоновые задачи и отмена

- загрузка модели, декодирование, waveform и транскрибация выполняются вне UI-потока;
- отмена кооперативная и происходит в безопасной точке;
- освобождайте модель, файлы и worker после завершения или ошибки;
- не перезапускайте долгую задачу на другом устройстве без подтверждения пользователя;
- частичный результат после отмены не уничтожается, если уже есть распознанный текст;
- закрытие приложения во время задачи требует явного решения пользователя;
- исключения worker не должны аварийно завершать UI.

## 11. Модели

- не коммитьте веса моделей;
- не скачивайте модели в unit-тестах;
- каталог моделей содержит зафиксированные источники, ревизии, размеры и контрольные суммы;
- загрузка идёт во временную папку;
- модель становится установленной только после проверки целостности;
- незавершённый файл нельзя загружать в inference runtime;
- обновление приложения не заменяет молча установленную модель;
- аппаратные требования считаются предварительными до собственного benchmark;
- изменение набора моделей требует обновления спецификации и benchmark-плана.

## 12. Словари

- встроенные словари хранятся в версионируемом формате;
- пользовательский `.txt` читается как UTF-8;
- пустые строки и дубликаты удаляются;
- число терминов и длина строки ограничиваются;
- словарь передаётся через поддерживаемый механизм подсказок адаптера;
- не выполняйте нечёткую автоматическую замену медицинских терминов;
- не записывайте содержимое пользовательского словаря в лог;
- источники встроенных терминов и их лицензии должны быть проверяемыми.

## 13. Приватность и безопасность

- аудио и расшифровка никогда не отправляются в сеть;
- сетевой доступ допускается только после явного действия для загрузки модели или проверки обновления;
- не добавляйте аналитику, crash reporting и telemetry SDK;
- не логируйте текст, фрагменты аудио и содержимое словарей;
- не храните секреты и токены в репозитории;
- не включайте абсолютные пользовательские пути в публичные отчёты;
- проверяйте внешние URL, контрольные суммы и лицензии;
- не выполняйте загруженные файлы как код;
- аудиофайл открывается только для чтения.

## 14. Зависимости

- добавляйте зависимость только при реальной необходимости;
- перед добавлением проверьте лицензию, поддержку Windows и размер сборки;
- runtime- и dev-зависимости разделяются;
- не смешивайте несколько менеджеров окружения и lock-файлов;
- изменения зависимостей отражаются в `pyproject.toml` и документации сборки;
- избегайте зависимости ради функции, которую можно надёжно реализовать небольшим количеством кода;
- не обновляйте все зависимости в рамках несвязанной задачи.

## 15. Тестирование

После появления конфигурации базовый набор команд:

```powershell
python -m pytest
python -m ruff check .
python -m ruff format --check .
python -m mypy src
```

Правила:

- unit-тесты быстрые, детерминированные и без сети;
- внешние сервисы, скачивание и inference адаптеры подменяются test doubles;
- integration-тесты используют короткие легально хранимые fixtures;
- большие модели и многочасовые записи запускаются отдельным профилем;
- GPU-тесты помечаются и корректно пропускаются без NVIDIA;
- для исправления ошибки сначала добавляется воспроизводящий тест, если это практично;
- тестируйте ошибки, отмену и восстановление, а не только успешный путь;
- QML должен иметь smoke-тест запуска и тесты ключевых состояний;
- Windows-упаковка проверяется на чистой VM.

Не утверждайте, что функция проверена, если выполнялся только mock-тест интеграции.

## 16. Git и файлы

- сохраняйте изменения узкими и тематически связанными;
- не перезаписывайте несвязанные пользовательские правки;
- не используйте destructive Git-команды без прямого запроса;
- не коммитьте модели, пользовательские аудиофайлы, результаты транскрибации, кеши и локальные настройки;
- не добавляйте generated-файлы, если они воспроизводимы при сборке и не нужны репозиторию;
- временные файлы удаляются до завершения задачи;
- новые файлы должны находиться в структуре, описанной спецификацией.

## 17. Документация

- `PROJECT_SPEC.md` описывает продукт и ожидаемое поведение;
- `IMPLEMENTATION_PLAN.md` описывает порядок реализации;
- `README.md` предназначен для пользователя и нового разработчика;
- `docs/model-benchmark.md` содержит воспроизводимые измерения;
- `docs/privacy.md` описывает локальные данные и сеть;
- значимые архитектурные решения фиксируются отдельными ADR в `docs/adr`;
- не оставляйте документацию, противоречащую коду.

## 18. Условия готовности изменения

Изменение готово, когда:

- соответствует спецификации;
- имеет тесты пропорционально риску;
- не блокирует UI;
- сохраняет локальную приватность;
- корректно обрабатывает ошибку и отмену;
- работает с кириллицей и путями Windows;
- учитывает reduced motion, если затрагивает UI;
- не добавляет скрытую сеть;
- проходит релевантные проверки;
- документация обновлена;
- в отчёте перечислены выполненные и невыполненные проверки.

## 19. Когда остановиться и спросить

Запросите решение владельца проекта, если требуется:

- изменить зафиксированный scope MVP;
- заменить основной стек;
- добавить облачную обработку или телеметрию;
- изменить список пользовательских моделей;
- автоматически исправлять медицинские термины после распознавания;
- добавить зависимость с неоднозначной лицензией;
- ослабить приватность или проверку целостности;
- выполнить разрушительную миграцию пользовательских данных;
- выбрать между вариантами, заметно меняющими UX или размер релиза.

Во всех остальных случаях выбирайте минимальное, обратимое и проверяемое решение, согласованное с текущим этапом плана.
